## 2. What went well

- **Contract-first paid off.** The pre-flight story (4-1) caught the **PRD-says-12 / scenario-file-says-13** count drift *before* any engine code — avoiding building and testing against the wrong scenario count. The delta (scenario 13 = payday-today ÷0 guard) was locked in writing.
- **The architectural "load-bearing wall" held (AD-1/AD-2/AD-14).** The engine is framework-agnostic pure `Decimal` — no `reflex`, no `finance_app` — so it built and tested with a **pytest-only venv** (no camelot/pandas/psycopg2). `tests/test_service_boundary.py` auto-covered every new module.
- **Zero-LLM was enforced, not promised.** The autouse `_forbid_anthropic` fixture makes any accidental SDK reach fail loudly. The 13-scenario suite is a single green go/no-go.
- **Out-of-order build validated.** Epic 4 was built ahead of E2/E3 because it is pure and contract-defined. The honesty/safety spine is complete and never faked a number.
- **Deferred-work discipline.** Real gaps (scenario-3 after-income, the `score_events` writeback) were flagged and tracked, not faked or silently resolved.

## 3. What was hard — lessons learned

- **A scenario suite covers enumerated cases, not every code path.** The `surfaced_predictions` bug passed all 13 scenarios (none exercise a predicted commitment due *after* payday) — code review caught it, not the gate. *Lesson: targeted path-level unit tests are complementary to the scenario suite, not redundant.*
- **The pre-flight contract locked the headline number but not the secondary outputs.** The **after-income** model gap (scenario-3 engine ₹1,830 vs file ~₹990) and the **`safety_ok` semantics** (balance≥reserved vs pool≥0) only surfaced when the engine actually computed. *Lesson: the contract should pressure-test derived/secondary evidence-pack fields, not just the hero STS.*
- **AD-13 applies to engine-produced prose too.** The engine embedded raw `₹9500` in its evidence/driver strings; `formatINR`/`formatDate` were treated as a UI-only rule. Caught in review and fixed. *Lesson: add "AD-13 applies to engine evidence strings" to the dev checklist.*
- **An AC that straddles a service/UI boundary needs its split planned up front.** CS-3 (event binding) split across 4-3 and 4-4 because AD-2 forbids the engine importing the `ScoreEvent` `rx.Model`; the DB writeback is still deferred to Epic 5. *Lesson: identify boundary-spanning ACs during story creation.*

## 5. Next epic preview — Epic 5 (Dashboard & Briefing) & dependencies on Epic 4

Epic 5 wires the engine into `DashboardState` `rx.State` handlers (AD-3 — the engine is the *sole* financial-state mutator) and performs the deferred `score_events` writeback. It inherits three concrete items from Epic 4:

1. **`Commitment` → `CommitmentInput` adapter (unbuilt).** The engine takes classified inputs (`due_date`, `is_predicted`, `amount_min`); the persisted `Commitment` model only has `due_day: int`. This mapping is a Epic 5 concern.
2. **`score_events` writeback (DB half of CS-3).** The dashboard handler must insert a `ScoreEvent(score, delta, trigger_event, explanation, suggested_action)` row per score change using the `ScoreResult` fields, and read the UI score back from the latest row (AD-9). Needs the full app env (reflex/sqlmodel) + an integration test against throwaway SQLite.
3. **Two carried spec decisions** (see action items): scenario-3 after-income; PRD FR-4 "12 scenarios" wording.
4. **Charts must route currency through `formatINR` (AD-13 / Agent-Misread guard)** — `rx.plotly` renders raw numbers by default.

**No fundamental plan change** — Epic 5's design is sound; these are known, tracked items, not a rewrite. **No "epic update required" alert.**
