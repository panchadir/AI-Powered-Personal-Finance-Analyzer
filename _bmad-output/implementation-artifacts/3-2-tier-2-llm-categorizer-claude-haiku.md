# Story 3.2: Tier-2 LLM Categorizer (Claude Haiku)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user with uncategorized transactions,
I want the app to automatically categorize them using AI with a constrained category set,
so that I don't have to manually label every transaction the rules didn't recognize.

## Acceptance Criteria

Source: [epics.md — Story 3.2](../planning-artifacts/epics.md) (lines 473–489)

1. **Given** transactions remain uncategorized after Tier-1 rules, **When** the Tier-2 LLM categorizer runs, **Then** it calls `claude-haiku-4-5` via `messages.parse()` with a Pydantic model whose `category` field is a `Literal` enum defined in `services/categorize/schema.py` — free-text categories from the LLM are structurally impossible.
2. **And** each result stores `category_source='llm'`, `category_confidence` (float, never shown raw to user), and `reasoning`.
3. **And** the enum hard-constraint also prevents prompt injection: a hostile merchant string like `"IGNORE PREVIOUS INSTRUCTIONS"` cannot produce an invented category.
4. **And** the upload progress bar step 4 (`"AI Assist"`) fires with a real count when this step completes — completing the skeleton from Epic 2.
5. **And** LLM calls are made via a `Categorizer` interface (not direct SDK calls) — mockable for unit tests.
6. **And** `pytest tests/categorize/test_llm_categorizer.py` passes with all LLM calls mocked; no real API call is made during tests.
7. **And** for the demo fixture: the 3 AI-categorized transactions receive correct categories with `category_source='llm'` — **see Dev Notes "The demo fixture has nothing left for Tier-2 to do" for why this literal AC is now unsatisfiable and how to test this story instead.**

            """Return a new list (same length/order) with category/category_source/

### Project-context rules that bind this story
- **AD-7 (category enum hard-constraint):** the `Literal[Category]` field on `CategorizationResult` is what makes an invented category *structurally* impossible — this is the actual mechanism behind AC #3, not prompt wording. Import `Category` from `services/categorize/schema.py`; do not redeclare.
- **AD-2/AD-14 (dependency injection, framework-agnosticism):** `services/categorize/` must not import `reflex` or construct its own `anthropic.Anthropic()` client — the client is passed in, exactly like `StatementParser` implementations and `persist_transactions`'s `txn_model` parameter. `tests/test_service_boundary.py` will catch a `reflex` import automatically; it does **not** catch "constructs its own client" — that's a code-review-time check, not an automated one, so get it right the first time.
- **NFR-4 (cost & model routing):** `claude-haiku-4-5` only for this story, as a constant in `services/narrate/config.py`; batch the call (Task 2); mark the system prompt `cache_control: ephemeral`.

### Review Findings

_Code review 2026-07-10 (3 parallel adversarial layers — Blind Hunter, Edge Case Hunter, Acceptance Auditor — on the Story-3.2-scoped diff: `services/categorize/{protocol,llm_categorizer}.py`, `finance_app/state/upload_state.py`, `finance_app/models.py`, `services/ingestion/{schema,persist}.py`, `services/narrate/config.py`, the migration, and the test suite). 0 decision-needed · 5 patches · 4 deferred · 4 dismissed as noise._

**Patches (applied 2026-07-10):**
- [x] [Review][Patch] **Prompt delimiter breakout via unescaped `description_raw`** [services/categorize/llm_categorizer.py — `_build_user_message`] — hand-built `<transaction index="N"><description>...</description></transaction>` tags interpolated untrusted bank-narration text with no escaping; a description containing a literal `</description></transaction><transaction index="N">...` sequence could forge a sibling block and corrupt a *different* legitimate transaction's category/confidence/reasoning in the same batch — precisely what the delimiting was meant to prevent, and (per Blind Hunter) `reasoning` is free text with no structural guard, so a successful breakout could land injected content in a field that gets persisted and may be surfaced later (e.g. a future Copilot context). (blind+edge+auditor, high) — **Fixed:** switched to a JSON-encoded transaction list (`json.dumps`) instead of hand-built tags — JSON string escaping structurally prevents breakout, no manual escaping to get wrong. New test asserts a description containing `</description>`-like text can't break the request structure.
- [x] [Review][Patch] **One malformed/truncated LLM response silently discards Tier-2 for the *entire* upload, not just the offending row** [services/categorize/llm_categorizer.py] — `messages.parse()`'s internal Pydantic validation is all-or-nothing across the whole batch response; a single off-taxonomy category string or a response truncated by the fixed `_MAX_TOKENS=4096` (not scaled to batch size — a large statement's uncategorized count could exceed it) raises, and the exception wasn't caught inside `categorize()` — it relied on `upload_state.py`'s broad `except Exception`, silently reverting every row in the batch to Tier-1-only with no distinction from "nothing needed AI". (blind+edge, high) — **Fixed:** `_MAX_TOKENS` now scales with batch size (base + per-item budget, capped); the `messages.parse()` call + response handling is wrapped in `try/except` *inside* `ClaudeCategorizer.categorize()` (logged, returns input unchanged on failure) — the degrade-gracefully behavior is now the categorizer's own tested contract, not an accidental side effect of the caller's catch-all. (Known residual limitation, not solved by this patch: true per-row partial credit within a single failed batch would need a bigger response-shape change — deferred, see below.)
- [x] [Review][Patch] **Duplicate-index results are applied instead of left `UNCATEGORIZED`, contradicting this story's own explicit task text** [services/categorize/llm_categorizer.py] — Task 2 says verbatim "if the LLM omits an index or returns a duplicate, leave that transaction as UNCATEGORIZED (never crash, never guess)"; the shipped code instead kept the *first* of two duplicate-index results and applied it — arbitrary selection among conflicting outputs, exactly the "guessing" the task text says to avoid. (auditor, medium) — **Fixed:** any index appearing more than once in the response is now excluded entirely (both/all duplicates dropped, row stays `UNCATEGORIZED`), matching the literal instruction. (blind+edge, medium — reframed, not a defect) — **Clarified, not changed:** the counting logic was correct; added an explicit comment (and a docstring on the new pure summary function, next finding) stating the confidence-threshold rule and why it must match `transactions_state.py`, so this can't be mistaken for a bug again.
