# Story 7.3: Insights Page & Dismiss Lifecycle

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user who has reviewed an insight,
I want to dismiss it so it doesn't clutter my feed, and have it resurface only if the underlying pattern materially changes,
so that my Insights page stays useful over time.

## Story Context

**Epic 7 — Proactive Insights, story 3 of 4.** Stories 7.1 (done, reviewed — `services/engine/insights/`, five deterministic detectors) and 7.2 (done, reviewed — `services/narrate/insight_narrator.py`, O→E→E→A prose + SEBI guard) are both pure backend with no UI. **This is the story where Insights becomes real and visible**: a dedicated page, real persistence, the dismiss lifecycle, and the "Ask Copilot" handoff that Story 6.4 already built the *receiving* side of.

**What this story delivers:**
1. A `finance_app/state/insights_bridge.py` (plain functions, mirrors `engine_bridge.py`'s established pattern) that maps DB rows → Story 7.1's `TxnRecord`/`CommitmentRecord`/`InsightContext`, runs `run_all_detectors`, maps each surviving `InsightCandidate` → Story 7.2's `InsightNarrationInput` (the exact conversion Story 7.2's own Dev Notes assign to "Story 7.3's caller"), calls `generate_insight_narration`, and persists/dedupes against existing rows.
2. A schema migration adding the columns the AC needs that don't exist yet (`dismissed_at`, `severity`, `metric_value` — see "Schema gap" below).
3. A new `MATERIAL_CHANGE_THRESHOLD_PCT` constant in `services/engine/insights/config.py` (does not exist yet — confirmed by repo-wide search).
4. `finance_app/state/insights_state.py` (`InsightsState(AuthState)`) — page-load orchestration, dismiss handler, empty states.
5. Real `finance_app/pages/insights.py` (replacing the placeholder), styled from the WDS prototype's existing CSS classes (`.insights-header`, `.insight-card`, `.evidence-block`, etc. — already compiled into `assets/wds.css`, no new CSS needed).

**What this story does NOT deliver (explicit scope boundary — do not build):**
- ❌ The Dashboard-side insight teaser card (pattern name + Observation-only + "See all insights →") → **Story 7.4**. Note: `dashboard.py`'s existing generic "See my insights →" button (Story 5.3) is unrelated and already there — don't confuse it with 7.4's teaser.
- ❌ Any change to `services/narrate/copilot.py` / `copilot_state.py` / `pages/copilot.py` — the "Ask Copilot" receiving side (context chip, `insight_id` in the POST body, `pre`-param pre-fill) is **already fully built** by Story 6.4. This story only needs to produce a correctly-shaped `/copilot?insight={id}&pre={text}` link — see "Ask Copilot contract" below.
- ❌ Changing any Story 7.1 or 7.2 source file. This story is purely the caller/bridge + UI layer, exactly as both of those stories' own Dev Notes anticipated.
- ❌ A literal REST endpoint (`POST /insights/{id}/dismiss`, as the PRD's FR-8.4 phrasing suggests). This app has no REST layer anywhere else (Commitments' add/edit/delete, Copilot's context-dismiss — all are `rx.State` event handlers). Resolve this the same way: `InsightsState.dismiss_insight(insight_id: int)` is an event handler, not a route.

## Acceptance Criteria

1. **Dedicated Insights page**, reachable from the persistent left nav (already fully wired — `finance_app/components/nav.py`'s `_TABS` already includes Insights; `finance_app/pages/insights.py`'s current placeholder already calls `side_nav("insights")`). Separate from the Dashboard.
2. **Each insight card shows:** pattern name (title), the four O→E→E→A sentences as prose, a "Dismiss" button, and an "Ask Copilot" button.
3. **Ordering:** newest-first within severity tier (`critical` → `important` → `flexible`).
4. **FR-8.5 footer note:** when the user's `data_months < MIN_DATA_MONTHS_FOOTNOTE` (3), a footer reads exactly `"More data sharpens these patterns."` — hidden at 3+ months. **Note:** the WDS prototype's own footer copy ("Based on 1 month of data...") is *not* this string — use the PRD/epics exact string, not the prototype's placeholder text (same "prototype layout yes, prototype microcopy not always" pattern already established in this codebase).
5. **Dismiss processes as:** `status` set to a dismissed value and `dismissed_at` stamped (a new column — see Schema gap) in the `insights` table; the card is removed from the *active* feed immediately via an optimistic `rx.State` update (query only active-status rows for the main list — this resolves the epics.md-vs-PRD tension: PRD's FR-8.4 restates the same idea as "moves to a collapsed section," but no collapsed-section UI exists in the WDS prototype or is required by epics.md's literal Given/When/Then; build the simpler, explicitly-specified behavior).
6. **Re-surface rule:** a dismissed pattern does not re-surface for the same user unless its headline metric changes by ≥`MATERIAL_CHANGE_THRESHOLD_PCT` (a **new** named constant this story adds to `services/engine/insights/config.py` — confirmed via repo-wide search that no such constant exists yet, despite the epics.md AC saying "the threshold is a constant in `services/engine/insights/config.py`," phrased as if it already existed). When it does change materially, a **new** `Insight` row is created — the old dismissed row is never un-dismissed.
7. **"Ask Copilot" contract:** tapping it lands on `/copilot?insight={insight.id}&pre={text}` — this exact query-string contract is already fully consumed by Story 6.4's `CopilotState.load_history` (reads `insight`/`pre` params, looks up the `Insight` row scoped by `user_id`, sets the "Talking about: {pattern_name}" chip, and later embeds `[insight_id=...]` in the outgoing chat message). This story only builds the *link*; nothing downstream needs to change.
8. **Empty states (FR-8.4):** when the user has no active insights at all (all dismissed, or none detected yet), show graceful copy, not a blank page. When `data_months` signals insufficient data (informational only — the detectors themselves already return `[]` rather than a low-confidence guess per Story 7.1's own honesty design), the page still renders without error.
9. **No arithmetic on this page or in its bridge.** Every number shown comes from `Insight` columns that were themselves populated verbatim from Story 7.1's `metrics`/Story 7.2's narration — `insights_bridge.py` maps and persists, it does not compute a financial figure (AD-1).

    1. Look up an existing **active** row for `(user_id, dedup_key)`. If found: if the new `metric_value` has **not** materially changed vs. that row's stored value, do nothing — leave the existing active row as-is (this is the common, no-change, every-page-load case; it must NOT create a duplicate). If it **has** materially changed, update that same row in place (re-narrate, overwrite `observation`/`explanation`/`effect`/`action_suggestion`/`metric_value`/`created_at`) — there is never more than one active row per `dedup_key` at a time.
    2. Otherwise, look up the most recent **dismissed** row for `(user_id, dedup_key)`. If found and the new `metric_value` has **not** materially changed vs. its stored value, do nothing — it stays correctly suppressed. If found and it **has** materially changed, or if no dismissed row exists at all (first time this identity has ever been seen), narrate via `generate_insight_narration` and insert a **brand-new** `Insight` row (`status="active"`) — never un-dismiss the old row (epics.md's explicit wording).
    - `_materially_changed(new, old) -> bool`: if `old is None or old == 0`, return `new != 0` (zero-guard, avoids `ZeroDivisionError`); otherwise `abs(new - old) / abs(old) * 100 >= MATERIAL_CHANGE_THRESHOLD_PCT`.
    - Rows whose `dedup_key` simply doesn't appear in the current candidate list (a pattern that stopped firing) are left untouched — this story does not auto-expire/auto-dismiss them; nothing in the ACs asks for that.
    - Return the current active rows for `user_id`, ordered per AC #3 (severity tier, then newest-first within tier).
  - [x] **Dedup key computation:** `dedup_key = candidate.pattern_name` for 4 of the 5 patterns; for `"Zombie subscriptions"` specifically, `dedup_key = f"{candidate.pattern_name}::{candidate.metrics['merchant']}"` (the merchant is always present in that detector's `metrics`, confirmed in `detectors.py`) — so two simultaneously-recurring merchants (e.g. Netflix and Spotify) get distinct identities, dedup/dismiss/resurface independently, and neither silently drops the other.

## Dev Notes

### Schema gap — 3 new columns, confirmed missing by direct inspection

Read `finance_app/models.py`'s current `Insight` class directly: `user_id, pattern_name, observation, evidence, explanation, action_suggestion, status, created_at`. **No `dismissed_at`, no `severity`, no metric-comparison column.** Story 7.1's own Dev Notes already flagged the missing `dismissed_at` as "a Story 7.3 concern." This story's own AC #6 additionally requires ordering by severity (not persisted today) and a materially-changed check (needs *something* to compare against — not persisted today either). All three are added in one migration (Task 1) rather than three, since they land in the same story.

### Headline metric per pattern (for AC #6's ≥15% comparison)

None of Story 7.1's 5 detectors expose a single obviously-canonical "the" metric — each has several. Pick one per pattern as `metric_value` (this is a judgment call, not specified anywhere; the values below are the most natural "how much has this pattern changed" figure per detector, and match the same per-pattern framing Story 7.2's fallback narrator already uses for its "Effect" sentence):

| `pattern_name` | `metrics` key used as `metric_value` |
|---|---|
| `"Post-payday spike"` | `spike_pct` |
| `"Death by small purchases"` | `total` |
| `"Zombie subscriptions"` | `monthly_amount` |
| `"Weekend vs weekday pace"` | `ratio` |
| `"Upcoming commitment collision"` | `projected_shortfall` |

An unrecognized future pattern name (mirrors Story 7.2's own generic-fallback precedent) has no defined headline metric — treat it as always materially different from any prior dismissed row of the same name (i.e., always let a new, unrecognized pattern surface) rather than crashing on a missing mapping.

### Corrected resurface algorithm — why the epics.md AC prose alone is not enough to implement from

Read literally, epics.md's Given/When/Then only describes two scenarios: "dismiss creates no resurface unless ≥15% changed" and "≥15% changed creates a new row." It never states what happens on an ordinary page load where **nothing changed and the pattern is already active** (the overwhelmingly common case — every detector run that finds the same steady pattern would otherwise create a fresh duplicate row every single time the page loads, since "no matching dismissed row exists" would trivially be true and nothing gates the active-and-unchanged case). Task 4's state machine above closes this gap explicitly: an existing **active** row is left alone when unchanged, and updated in place (not duplicated) when changed; only the **dismissed** row path ever creates a brand-new row, exactly matching epics.md's literal "a new insight row is created; the old dismissed row is not un-dismissed" wording, which is scoped to the dismissed case only.

### Multi-instance patterns and `dedup_key`

Confirmed by reading `services/engine/insights/detectors.py` directly: `ZombieSubscriptionDetector.detect()` groups by merchant and appends one `InsightCandidate` per qualifying merchant, so a single `run_all_detectors()` call can return **two or more** candidates that all share `pattern_name == "Zombie subscriptions"`. Every other detector returns at most one candidate. Using bare `pattern_name` as the resurface/dedup identity (as a first draft of this story did) would conflate two unrelated recurring subscriptions into "the same insight" — dismissing a Netflix insight would suppress a completely unrelated Spotify one. The `dedup_key` column (Task 1) and its per-pattern computation rule (Task 4) exist specifically to keep these independent.

### Why `data_months` isn't a new column

`InsightCandidate.data_months` (Story 7.1) is a property of the **detection run**, computed from `ctx.transactions` — all candidates from one `run_all_detectors(ctx)` call share the same value. Storing it per-`Insight` row would go stale the instant the user uploads more data without every existing row being touched by a fresh detector run (which this story's on-page-load `refresh_insights` doesn't retroactively do for already-persisted rows). The footer's `data_months` is therefore computed **fresh** at page-load time from the user's live transaction history (Task 3's promoted `data_months` utility), not read off any one `Insight` row — always current, never stale.

### Detector-run trigger — on Insights-page-load, not an ingestion webhook

FR-8.1's epics.md wording ("triggered after every successful ingestion or categorisation batch") describes an event-driven trigger that doesn't exist yet — Epic 3 (categorization) is still `backlog` in `sprint-status.yaml`, and Epic 2 (ingestion) has no post-parse hook into Epic 7. Mirroring Story 7.1's own precedent of being "built ahead of" the epics it nominally depends on, this story runs detection **on Insights-page load** (`InsightsState`'s `on_load`, calling `refresh_insights`) rather than waiting for a webhook that isn't there. This is a pragmatic, self-contained resolution — not a silent scope cut, since the AC's actual observable behavior ("the Insights page shows fresh patterns") is satisfied either way. When Epic 3's categorization pipeline lands, a future story can add the same `refresh_insights` call as a post-ingestion hook without changing this story's own code.

### Established pattern to mirror: `finance_app/state/engine_bridge.py` + `dashboard_state.py`

`engine_bridge.py` is deliberately a **plain module of functions, not an `rx.State`**, so the DB↔engine round trip is unit-testable without booting Reflex (mirrors this story's own `insights_bridge.py`). Concrete functions to reuse rather than reimplement: `load_transactions(session, user_id)`, `load_commitments(session, user_id)` — both already map DB rows into engine-compatible plain types; `insights_bridge.py` should call these, not duplicate them, then further map into Story 7.1's `TxnRecord`/`CommitmentRecord` shapes. `dashboard_state.py` shows the `rx.State`-side conventions to mirror: `on_load` opens its own DB session, checks auth (`user_for_token(session, self.auth_token)` → `None` triggers `yield rx.redirect(LOGIN_ROUTE); return` — note the `yield` before `return` in an async generator, a bare `return <value>` is illegal there), converts engine/bridge output to plain display strings before it ever touches a Reflex state var, and treats narration failures as non-fatal (never crashes the page).

### Ask Copilot contract — already fully built on the receiving side (Story 6.4)

The chip (`_context_chip()` in `copilot.py`) renders "Talking about: {pattern_name}" whenever `context_pattern_name != ""`. `send_message` already prefixes `f"[insight_id={self.context_insight_id}] {text}"` onto the outgoing chat turn when set. **This story changes none of that** — it only needs to produce the link `f"/copilot?insight={insight_id}&pre={quote(advice_text)}"` (URL-encode the `pre` text; the WDS prototype's own JS does this via `URLSearchParams`, mirror that intent with `urllib.parse.quote`/`rx.State`'s own param-building idiom).
