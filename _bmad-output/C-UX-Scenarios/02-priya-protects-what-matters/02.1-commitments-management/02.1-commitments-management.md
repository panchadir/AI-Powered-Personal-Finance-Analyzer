## Overview

**Page Purpose:** Let Priya add her electricity bill as a protected commitment — name, amount, due-day, criticality — and see her Safe-to-Spend number update in real-time to confirm it's now ring-fenced.

**User Situation:** Priya logged back in specifically for this. She's purposeful and focused. She knows what she wants to do. The page needs to make the task obvious in 2 seconds and the Safe-to-Spend recalculation needs to be visually satisfying — the moment the number updates is the moment she feels protected.

**Success Criteria:** Priya adds her electricity bill with 4 fields (or fewer, with smart defaults), clicks save, sees the Safe-to-Spend number decrease by the bill amount in real-time, and understands that the bill is now protected — she can't accidentally spend that money before the due date.

**Entry Points:**
- Dashboard: "+ Add a commitment" from the Commitments Timeline card — the **sole** entry point (2026-07-09, corrected: Commitments is not a persistent sidebar item, matching FR-6.4's 4-screen nav)
- Scenario 02: post-login redirect if `returnTo=/commitments`

**Exit Points:**
- "Done" / close → Dashboard (Safe-to-Spend now updated)

## Page States

| State | When | Appearance | Actions |
|-------|------|------------|---------|
| Default (no commitments) | First visit, no commitments yet | Empty list state; Add CTA prominent | Click Add |
| Default (with commitments) | Has existing commitments | List of rows; impact bar showing total | Click to edit, click Add |
| Modal open (add) | Add CTA clicked | Modal opens as a centered overlay (fade/scale in); form empty | Fill fields, save or cancel |
| Modal open (edit) | Existing row clicked | Modal with pre-filled fields | Edit, save or cancel |
| Saving | Save clicked | Spinner on save button; fields disabled | Wait |
| Save success | API returned success | Modal closes; new row appears in list with soft flash; impact bar updates (Safe-to-Spend decreases) | Continue adding or return to Dashboard |
| Delete confirm | Delete selected from row menu | Confirmation dialog: "Remove {name}? Your Safe-to-Spend will update." | Confirm or cancel |
| Error — save failed | API error | Toast: "Couldn't save that — please try again" | Retry |

## Data / API

| Action | Endpoint | Method | Payload | Response |
|--------|----------|--------|---------|----------|
| Load commitments | `/commitments` | GET | — | `[ { id, name, amount, due_day, criticality } ]` |
| Add commitment | `/commitments` | POST | `{ name, amount, due_day, criticality }` | `{ id, safe_to_spend_updated }` |
| Edit commitment | `/commitments/{id}` | PATCH | `{ name?, amount?, due_day?, criticality? }` | `{ safe_to_spend_updated }` |
| Delete commitment | `/commitments/{id}` | DELETE | — | `{ safe_to_spend_updated }` |

**Real-time Safe-to-Spend update:** The API response includes the updated `safe_to_spend` figure; the client updates the impact bar chips immediately on success. No separate dashboard fetch needed.

## Accessibility

- Modal has `role="dialog"` with `aria-labelledby` pointing to the modal header
- Modal opens with focus moved to the first field; focus is trapped within the modal until dismissed
- Escape key closes the modal (equivalent to "Cancel")
- Criticality chips have `aria-pressed` / `aria-selected` for selected state
- Impact bar chips update with `aria-live="polite"` on save (announces new Safe-to-Spend total)
- Delete confirmation dialog traps focus until resolved

---

## Technical Notes

- **"Protect" language throughout** — every button, label, and description uses protection/ring-fencing framing. Never "save" or "add bill." The emotional payoff is about safety, not data entry.
- **Real-time update on save** — the Safe-to-Spend number in the impact bar must animate when a new commitment is saved (e.g., counts down from old to new value over 600ms). This is the key UX moment — Priya sees the protection happen.
- **Conservative-by-default** — if Priya forgets to set criticality, the default is "Important" (not "Flexible"). We never allow ambiguity to result in under-protection.
- **Day-31 handling** — for months shorter than 31 days, a "due 31st" commitment defaults to the last day of the month. The UI can show "end of month" as a display label for day 31.
