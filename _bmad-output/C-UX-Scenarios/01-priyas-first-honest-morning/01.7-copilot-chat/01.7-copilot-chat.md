## Overview

**Page Purpose:** Deliver Priya's first experience of asking a real financial question and getting an answer that is traced entirely to her own data — establishing the Copilot as a trustworthy, honest financial voice before she has any reason to test its limits.

**User Situation:** Priya just saw a real named pattern in her spending on the Insights page. She's intrigued — the app clearly knows her data. She opens the Copilot curious: *"What else can it tell me?"* This is exploratory, not a high-stakes decision. She asks something like "how am I doing?" or follows up on the post-payday insight. If the Copilot gives a confident answer using real numbers traced to her data, she'll be back. If it hedges every sentence or invents numbers, she won't.

**Success Criteria:** Priya asks at least one question, receives an answer that:
1. Uses her actual transaction/Safe-to-Spend data (no invented numbers)
2. Explicitly notes confidence level where uncertain
3. Streams token-by-token so she sees it "thinking"
4. Ends with a traceable citation ("based on your July transactions")

She exits the app for the first time feeling more informed and calmer than when she arrived.

**Entry Points:**
- "Ask the Copilot about this" from 01.6 AI Insights (with pre-populated context)
- Left sidebar "Copilot" item (direct access, no pre-population)

**Exit Points:**
- Close app / navigate away — scenario complete ✓
- Left sidebar: back to Dashboard, Transactions, Insights (Commitments is reached via the Dashboard's "+ Add a commitment" CTA, not the sidebar)

## Page States

| State | When | Appearance | Actions |
|-------|------|------------|---------|
| First-visit empty | Copilot opened for first time | Welcome card + suggestion chips | Tap chip or type |
| Pre-populated | Arrived from Insights with context | Context chip + pre-populated input; suggestion chips adjusted | Edit message or send |
| User typing | Cursor in input field | Keyboard open; send button enabled when text present | Continue typing, send |
| Awaiting response | Message sent, response not yet started | Copilot bubble with pulsing dots ("thinking…") | Wait |
| Streaming | Response in progress | Token-by-token text appearing; cursor blinking | Read; can scroll up |
| Response complete | Full response received | Response + data trace chips visible; input cleared | Follow up, tap trace, navigate |
| Error — response failed | API error during streaming | Copilot bubble: "Something went wrong — I couldn't complete that response. Try again?" with retry tap | Retry |
| Error — out of context | Question outside Copilot's data scope | Honest response: "I don't have enough data to answer that well. [what would help]" | Upload more data |
| Recurring visit | Returning to Copilot after previous session | Conversation history shown (last session); new input bar empty | Continue conversation or start fresh |

## Data / API

→ [data-api.instructions.md](../../../.claude/skills/wds-4-ux-design/templates/instructions/data-api.instructions.md)

| Action | Endpoint | Method | Payload | Response |
|--------|----------|--------|---------|----------|
| Send message | `/copilot/chat` | POST | `{ message, context?: { insight_id, session_id } }` | `stream: Server-Sent Events (SSE)` — token-by-token |
| SSE stream format | — | — | — | `{ type: 'token', text: '...' }` \| `{ type: 'trace', sources: [...] }` \| `{ type: 'done' }` |
| Load history | `/copilot/chat/history` | GET | — | `[ { role, text, trace?, timestamp } ]` |

**Streaming:** Server-Sent Events (SSE) preferred over WebSocket for one-directional text streaming — simpler and stateless for this use case. Fallback: polling (not recommended).

**Honesty enforcement:** The system prompt for the Copilot LLM must include:
1. "Never invent financial figures. Only use numbers present in the user's actual transaction data."
2. "When uncertain, express uncertainty explicitly (e.g., 'based on the data I have', 'I'm not sure but it looks like')."
3. "Never give investment recommendations. Information only."
4. "Always cite data sources in the trace field."

## Accessibility

→ [accessibility.instructions.md](../../../.claude/skills/wds-4-ux-design/templates/instructions/accessibility.instructions.md)

- Chat thread uses `role="log"` with `aria-live="polite"` for screen reader streaming announcements
- Streaming response: each completed sentence is announced; mid-stream tokens are batched (not announced one-by-one — would be noise)
- Input field has `aria-label="Message to AI Copilot"`
- Send button `aria-disabled="true"` when empty (not `disabled` — stays in tab order)
- Data trace chips have `aria-label="{source description}"` (not just abbreviated chip label)

## Technical Notes

- **SSE streaming over WebSocket** — SSE is simpler, stateless, and a good fit for one-directional token streaming; no bidirectional channel is needed for this feature
- **Session persistence** — conversation history is stored server-side (not localStorage) for cross-device consistency and DPDP compliance
- **Context from Insights** — `insight_id` in the POST body allows the server to pre-load the relevant insight data into the Copilot's context window without Priya needing to describe the insight again
- **Data trace is server-generated** — the LLM must emit structured trace data alongside the response text; the client renders it as chips. The trace must come from the server, not be inferred client-side from the response text (too fragile)
- **"I don't know" is a valid response** — the system must handle out-of-scope questions gracefully; a confident-sounding wrong answer is far worse than an honest "I don't have enough data for that"
- **This page is shared with Scenario 03** (03.1 Copilot Chat) — the UI is identical; the difference is the pre-populated context (first-touch exploratory vs. habitual gut-check). The page spec for 03.1 documents only the state differences.
